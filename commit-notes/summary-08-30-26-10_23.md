## Overview

This commit resolves a critical deployment bottleneck where publishing the ML Lambda layer directly via Terraform exceeded the AWS Lambda API 50MB direct upload threshold, and fixes runtime C-extension import issues in NumPy and Scikit-Learn. It migrates the layer distribution model to an S3-backed staging mechanism (`aws_s3_object`) referenced dynamically by `aws_lambda_layer_version`. In addition, dependency versions are locked to `scikit-learn==1.7.2` and `numpy==2.2.6` using pre-compiled binary wheels, and aggressive pruning in the Docker build script is adjusted to preserve essential C-extension metadata and package submodules.

## Files Changed

### Infrastructure as Code (Terraform)
- **`terraform/layers.tf`**: Introduces an `aws_s3_object` resource (`layers/sklearn-layer.zip`) to stage the 70MB+ compressed layer artifact directly into S3, and refactors `aws_lambda_layer_version` to use `s3_bucket` and `s3_key` instead of direct local file uploads.
- **`terraform/lambda_ingestion.tf`**: Formats and explicitly attaches the source account attribute to the `aws_lambda_permission` resource for strict S3 invocation access.
- **`terraform/layers/sklearn-layer.zip`**: Bundled pre-built binary zip artifact containing compiled runtime wheels for Python 3.11 x86_64.

### Dependency & Packaging Scripts
- **`scripts/build_layer.sh`**: Updates pip installation flags with `--only-binary=:all:`, pins locked library versions (`scikit-learn==1.7.2`, `numpy==2.2.6`), and removes over-aggressive stripping of `.dist-info` and `test` directories that previously broke runtime NumPy symbol resolution.
- **`requirements.txt`**: Aligns local environment dependencies with the pinned layer versions (`scikit-learn==1.7.2`, `numpy==2.2.6`).

## Code Changes

### S3-Backed Layer Staging to Bypass 50MB Direct Upload Limit
In `terraform/layers.tf`, the Lambda Layer archive is uploaded directly to S3 via `aws_s3_object` before being referenced by `aws_lambda_layer_version`:
```hcl
# Upload layer zip archive to S3 bucket to bypass Lambda 50MB direct API upload limit
resource "aws_s3_object" "sklearn_layer_zip" {
  bucket = aws_s3_bucket.raw_transactions.id
  key    = "layers/sklearn-layer.zip"
  source = "${path.module}/layers/sklearn-layer.zip"
  etag   = fileexists("${path.module}/layers/sklearn-layer.zip") ? filemd5("${path.module}/layers/sklearn-layer.zip") : null
}

resource "aws_lambda_layer_version" "sklearn_layer" {
  layer_name               = "${var.project_name}-sklearn-layer"
  description              = "Scikit-Learn, NumPy, Joblib, and Pandas runtime dependencies for Python 3.11"
  s3_bucket                = aws_s3_bucket.raw_transactions.id
  s3_key                   = aws_s3_object.sklearn_layer_zip.key
  source_code_hash         = fileexists("${path.module}/layers/sklearn-layer.zip") ? filebase64sha256("${path.module}/layers/sklearn-layer.zip") : null
  compatible_runtimes      = ["python3.11"]
  compatible_architectures = ["x86_64"]

  depends_on = [
    aws_s3_object.sklearn_layer_zip,
  ]
}
```

### Safe C-Extension Compilation & Binary Wheel Pinning
In `scripts/build_layer.sh`, pip is instructed to strictly install binary wheels for Amazon Linux 2023 / Python 3.11, avoiding breaking shared objects during pruning:
```bash
echo '[Container] Installing locked ML libraries...'
python3.11 -m pip install \
    --no-cache-dir \
    --only-binary=:all: \
    --target '${TARGET_SITE_PACKAGES}' \
    scikit-learn==1.7.2 \
    numpy==2.2.6 \
    joblib==1.5.3 \
    pandas==3.0.5

echo '[Container] Stripping unnecessary files to optimize package size...'
find '${TARGET_SITE_PACKAGES}' -type d -name '__pycache__' -exec rm -rf {} + 2>/dev/null || true
find '${TARGET_SITE_PACKAGES}' -type f -name '*.pyc' -delete || true
find '${TARGET_SITE_PACKAGES}' -type f -name '*.pyo' -delete || true
```
